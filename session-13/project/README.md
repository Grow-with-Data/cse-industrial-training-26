# ShopWise v10 — the assistant becomes a web API

Session 13. Until now ShopWise ran in a terminal on your laptop. A customer on their phone cannot use a terminal. A React page cannot use one either, and neither can a mobile app or a partner's system. They all speak **HTTP**. This session puts the v9 team behind an HTTP API built with **FastAPI**. There is no notebook: you read the code in your editor and run it from a terminal.

> 💸 **Real model calls cost money.** Starting the server, opening `/scalar`, and creating, listing or
> deleting threads are all free. Sending a message (or resuming a refund) runs the graph, and the graph
> calls the model several times per turn.

## 1. Run it

```bash
cd labs/session-13/project
uv sync                                   # creates project/.venv (first time: a few minutes)
uv run fastapi dev                        # http://127.0.0.1:8000, reloads when you save a file
```

Then open **<http://127.0.0.1:8000/scalar>**, the API reference. Every endpoint is listed with its fields, its examples and every error it can return, and a **Test Request** button sends it for real.

| Task | Command |
| --- | --- |
| Run the API (reload) | `uv run fastapi dev` → `/health` = `{"status":"ok"}` |
| Run it, spelled out | `uv run uvicorn shopwise.main:app --reload` |
| Run it like production (no reload) | `uv run fastapi run` |
| API reference (Scalar) | open `/scalar` · Swagger UI at `/docs` · ReDoc at `/redoc` |
| The full story, request by request | open `requests.http` in VS Code (REST Client extension) |
| Export the contract | `uv run python scripts/export_openapi.py` → `docs/openapi.json` |
| Is the contract current? | `uv run python scripts/export_openapi.py --check` |
| Build the knowledge base | `uv run python -m shopwise.llm.kb.ingest` (once; shared with earlier sessions) |
| Print the settings | `uv run python -m shopwise.core.config` |
| Lint / format | `uv run ruff check .` / `uv run ruff format .` |
| Add a dependency | `uv add <pkg>` (dev: `uv add --dev <pkg>`), then commit `uv.lock` |

Keys are read from `labs/.env`, as in every session, and then from `project/.env` if you create one.
`project/.env` wins. `.env.example` lists every setting.

**Try it with curl** (needs a running server):

```bash
curl -s localhost:8000/v1/threads -H 'Content-Type: application/json' \
     -d '{"customer_email":"ayesha@example.com"}'
# 💸 stream a reply: -N turns off curl's buffering so frames appear as they arrive
curl -N localhost:8000/v1/threads/<id>/messages/stream -H 'Content-Type: application/json' \
     -d '{"text":"Can I return headphones I opened 10 days ago?"}'
```

> **The curl gotcha:** without `-H 'Content-Type: application/json'` FastAPI rejects the body with a
> 422. It does not guess that the body is JSON.

### 2.3 `src/shopwise/` — the package

#### `main.py`

Creates the app. `create_app()` builds the `FastAPI` object, registers middleware, error handlers and
routers, and mounts `/scalar`. `lifespan` opens the databases, builds the graph and the services
**once**, at startup, and closes them at shutdown. Start reading here.

#### `api/` — HTTP in, HTTP out

Everything that knows about HTTP lives here, and nothing below it does.

| Path | What it contains |
| --- | --- |
| `api/errors.py` | the four exception handlers that turn every error into RFC 9457 problem details (`application/problem+json`) |
| `api/middleware.py` | code around every request: the request id (`X-Request-ID`, stamped on every log line) and CORS |
| `api/v1/router.py` | registers every `/v1` endpoint module in one place |
| `api/v1/endpoints/threads.py` | `POST/GET /v1/threads`, `GET/DELETE /v1/threads/{id}`, `GET …/messages` (history) |
| `api/v1/endpoints/messages.py` | `POST …/messages` (wait for the reply) and `POST …/messages/stream` (Server-Sent Events) |
| `api/v1/endpoints/approvals.py` | `GET /v1/approvals` (the manager's inbox) and `POST …/resume` (approve, edit, reject; needs `Idempotency-Key`) |
| `api/v1/endpoints/health.py` | `GET /health` and `GET /ready`, unversioned |
| `api/v1/schemas/` | **API schemas**: what a client sends and gets back. One file per feature (`threads`, `messages`, `approvals`, `health`), plus `common.py` (thread status, the problem-details body, `problem_responses()` for the docs) |
| `api/v1/examples/requests.json` | the example requests `/scalar` shows, loaded with `examples("MessageIn")` |

**The rule:** an endpoint takes validated input, calls **one** service method, and returns an API
schema. No business logic.

#### `services/` — the use cases

One class per area of the product, one method per thing a user can do. Services know nothing about
HTTP: they raise `ShopWiseError` subclasses, and `api/errors.py` picks the status code.

| File | Class | What it does |
| --- | --- | --- |
| `thread_service.py` | `ThreadService` | create, get, list, delete threads; work out each thread's status (`idle`, `running`, `awaiting_approval`); one turn at a time per thread (`claim`/`release`) |
| `chat_service.py` | `ChatService` | send a message: `send()` waits for the whole reply, `start_stream()` streams it. Both run the same `run_turn()` |
| `approval_service.py` | `ApprovalService` | list paused refunds across threads; resume one with a manager's decision |
| `idempotency_service.py` | `IdempotencyService` | the Idempotency-Key pattern: run once, replay on retry, 422 on a reused key, 409 while in progress |
| `daily_brief.py` | — | [ADV] the Shop Owner's Daily Brief's gather steps (an API arrives in a later session) |

#### `db/` — storage

| File | What it contains |
| --- | --- |
| `db_manager.py` | `AppDatabase` (the API's own SQLite file, `labs/.state/api.sqlite`) and `open_resources()`, which opens the checkpointer, the memory store and `AppDatabase`, builds the graph, and closes everything in reverse order |
| `threads.py` | `ThreadRepository`: one row per thread (owner, title, dates); cursor pagination, newest first |
| `idempotency.py` | `IdempotencyRepository`: one row per Idempotency-Key (body hash, status, stored response), with expiry |

**Three SQLite files, three jobs:** `checkpoints.sqlite` is LangGraph's (every step of every
thread), `memory.sqlite` is LangGraph's Store (what ShopWise knows about each customer), and
`api.sqlite` is the API's (questions like "all threads, newest first" that a checkpoint file is not
built to answer).

#### `core/` — what every layer shares

| File | What it contains |
| --- | --- |
| `config.py` | `Settings` (pydantic-settings): every `SHOPWISE_*` setting, its default and why it exists. Run `uv run python -m shopwise.core.config` to print them |
| `constants.py` | fixed facts of the domain (the 30-day return window, …) |
| `exceptions.py` | `ShopWiseError` and every subclass. Each one carries its own `status_code`, `error_type` and `title`, so a service raises and never builds a response |
| `logging_config.py` | `setup_logging()`, `get_logger()`, and the request-id filter |
| `deps.py` | FastAPI dependencies: `ThreadServiceDep`, `ChatServiceDep`… hand a route the service `lifespan` built |

#### `llm/` — everything that talks to a model

Unchanged in behaviour from v9; gathered under one folder in v10.

| Path | What it contains |
| --- | --- |
| `models.py` | `build_model()` and the helpers every prompt goes through on its way to the model |
| `middleware.py` | the safety rails the agents run inside (session 4), plus `ShopContext`: whose ticket it is and who is acting (customer or manager) |
| `tools.py` | the eight tools the assistant may call (`get_order`, `search_policy`, `issue_refund`, …) |

| `schemas/<feature>/` | **LLM schemas**: what a model is asked to return (`triage`, `inbox`, `rag`, `memory`, `refund`, `supervisor`). Never the same classes as the API schemas |

#### `llm/workflows/` — the graphs

Every workflow has the same shape: `graph.py` wires it, `state.py` says what it remembers, and
`nodes/` holds **one node per file**. Helpers several nodes share sit in `_`-prefixed files, and

| Folder | What it is | Who runs it |
| --- | --- | --- |

| `specialists/` | the team members: `orders` (records over MCP), `knowledge` (policies and past tickets, a subgraph), `refunds` (calls the refund graph), `market` ([ADV] the open web). `mcp_client.py` starts the MCP server and calls its tools | the supervisor |
| `refund/` | one refund request: `assess` → `approval` (pauses with `interrupt()` for a manager) → `pay` | the `refunds` specialist |
| `corrective_rag/` | the policy graph: search, grade what came back, rewrite and search again if it is weak, answer with a citation | the knowledge path, and `evals/` |
| `memory/` | `recall` (load what ShopWise knows about a customer) and `remember` (save what this turn taught it); `store.py` opens the Store | the supervisor |
| `inbox/` | the v8 inbox graph. No longer the main graph, but its nodes (`intake`, `triage`, `compose`, the refund helpers…) are reused by the supervisor, and `open_saver()` lives here | the supervisor (nodes), `evals/multiagent_compare.py` |

#### `mcp_server/` — the records, as an MCP server

| File | What it contains |
| --- | --- |

| `audit.py` | reads a server's tool list before you connect an agent to it (session 12's security section) |
| `poisoned_demo.py` | a deliberately malicious server, for that same section. Never connected to the team |

#### `utils/streaming/` — between the graph and HTTP

| File | What it contains |
| --- | --- |
| `events.py` | the seven events the outside world sees (`token`, `progress`, `tool`, `citation`, `interrupt`, `done`, `error`) and `stream_ticket()`, which runs one turn and yields them. The API sends each one as an SSE frame |
| `bridge.py` | `start_in_thread()`: runs the synchronous graph in its own thread and hands its events to async code through a queue, so a long turn never blocks other requests |

1. `main.py`: how the app starts.

## 3. What changed from v9: two moves

A project changes shape one step at a time, and each step has a reason. This session makes two.

### Move 1 — the folder of scripts becomes a package

```
v9 (session-12/project)                 v10 (session-13/project)
├── chat.py   inbox.py   agent.py       ├── pyproject.toml   uv.lock   .python-version
├── models.py tools.py   schemas.py     ├── src/
├── middleware.py  shopwise_data.py     │   └── shopwise/          ← one importable package
├── core/   kb/   prompts/              ├── evals/                 ← stays at the root
├── workflows/   mcp_server/            ├── scripts/   docs/   requests.http
└── evals/                              └── README.md
```

**Why:** a web server, the MCP server and the evals all have to *import* ShopWise. A folder of scripts
offers nothing to import: each file only worked when you ran it from the right directory, after a
`sys.path` hack. With a package, every import is `from shopwise.… import …` and works from anywhere,
and `uv sync` installs it into `.venv`. The CLIs (`chat.py`, `inbox.py`) and the old v1/v6 scripts are
gone: from now on the API *is* how you talk to ShopWise.

### Move 2 — the API layer arrives, and everything that talks to a model gathers under `llm/`

What is new, folder by folder (section 2 describes every one):

| New in v10 | Was in v9 |
| --- | --- |
| `main.py`, `api/`, `services/`, `db/`, `utils/streaming/bridge.py` | nothing: the API layer did not exist |
| `core/logging_config.py`, `core/deps.py` | nothing |
| `llm/` (`models.py`, `middleware.py`, `tools.py`, `llm_data/`, `prompts/`, `schemas/`, `kb/`, `skills/`, `workflows/`) | the same files at the top level of the project |
| `llm/schemas/<feature>/` | one `schemas.py` |
| `llm/workflows/<feature>/nodes/` (one node per file) | one `nodes.py` per workflow |

**Why:** HTTP schemas arrive today. A client's view of a message (`api/v1/schemas/messages.py`) and
the model's structured output (`llm/schemas/triage/`) are different things that sometimes look alike.
Keeping them in two folders makes the rule visible: **API schemas and LLM schemas are never the same
class.** Rename a field the model returns, and no client breaks. Rename a field a client reads, and it
is a deliberate, reviewed change to `docs/openapi.json`.

Inside `llm/workflows/`, the long `nodes.py` files are split up, **one node per file** (the inbox's
568-line `nodes.py` became 15 files). Helpers that several nodes share live in the underscore files.
Each `nodes/__init__.py` re-exports every name, so `from shopwise.llm.workflows.inbox.nodes import
compose` still works.

## 4. How a request travels

```
client ──HTTP──▶ middleware (request id, CORS)
                   │
                   ▼
                 endpoint      api/v1/endpoints/messages.py   parse + validate, pick the status code
                   │
                   ▼
                 service       services/chat_service.py       the use case: "send a message"
                   │
                   ▼
                 graph         llm/workflows/supervisor/      the v9 team, unchanged
                   │
                   ▼
                 checkpoints · memory · Qdrant · refund ledger
```

**The rule: endpoints stay thin.** An endpoint does three things: it takes validated input, calls one
service method, and returns an API schema. If you find an `if` about refunds in an endpoint, it belongs
in a service. The test of a good layer is that you could swap the graph for a fake without touching a
single route.

### Adding a feature (the house rule)

| Layer | Where | What |
| --- | --- | --- |
| Endpoint | `api/v1/endpoints/<feature>.py` | `router = APIRouter()`; register it in `api/v1/router.py` |
| API schemas | `api/v1/schemas/<feature>.py` | request and response models |
| LLM schemas | `llm/schemas/<feature>/` | structured output. **Never merged with the API schemas** |
| Workflow | `llm/workflows/<feature>/` | `graph.py`, `state.py`, `nodes/` (one node per file) |
| Prompts | `llm/prompts/<feature>/` | YAML, loaded with `get_prompt()`. No inline prompt strings |
| Docs | `docs/api-reference.md` | index table, the section, the summary table: **three places** |

## 5. The FastAPI ideas in this codebase, and where to read each one

| Idea | One line | Read it in |
| --- | --- | --- |
| A route | a function + a decorator: `@router.get("/{thread_id}")` | `api/v1/endpoints/threads.py` |
| Validation for free | type the parameter as a Pydantic model; a bad body gets a 422 naming the field | `api/v1/schemas/messages.py` (`MessageIn`) |
| Response model | the return type annotation is the response's shape and its docs | any endpoint |
| Status codes | `status_code=201` on create, `204` on delete; errors carry their own | `threads.py` |
| Dependencies | `threads: ThreadServiceDep`: FastAPI builds or fetches it for you | `core/deps.py` |
| Lifespan | open databases and build the graph **once**, before the first request | `main.py` |
| `def` vs `async def` | a blocking call inside `async def` freezes every user; plain `def` runs in a worker thread | `threads.py` vs `messages.py`, `utils/streaming/bridge.py` |
| Streaming (SSE) | `response_class=EventSourceResponse` + `yield ServerSentEvent(...)` | `messages.py` |
| Checks before a stream | a dependency runs before the response starts, so a 404 is still possible | `messages.py` (`started_stream`) |
| Errors as a contract | every error is `application/problem+json`; clients branch on `type` | `api/errors.py`, `core/exceptions.py` |
| Middleware | code around every request: request id, CORS | `api/middleware.py` |
| Versioning | everything under `/v1`; a published path is a promise | `main.py`, `core/config.py` (`API_PREFIX`) |
| Docs | tags, summaries, `responses=`, `openapi_examples`, readable operation ids | every endpoint, `main.py` |

### Three things that differ from older tutorials you will find online

1. `Annotated[T, Depends(fn)]` is the idiom, not `x: T = Depends(fn)`.
2. Run the laptop server with `fastapi dev` and a production one with `fastapi run` (Gunicorn in
   session 16). Never `--reload` in production.
3. Server-Sent Events are built into FastAPI now (`fastapi.sse`). You no longer need `sse-starlette`.

## 6. The endpoints

| Method + path | Purpose | Notes |
| --- | --- | --- |
| `POST /v1/threads` | create a thread | 201 + `Location`; the server mints the id |
| `GET /v1/threads` | list threads | cursor pagination, newest first |
| `GET /v1/threads/{id}` | one thread + its status | `idle` · `running` · `awaiting_approval` |
| `GET /v1/threads/{id}/messages` | history | an API schema, never raw graph state |
| `DELETE /v1/threads/{id}` | delete thread + checkpoints | 204 |
| `POST /v1/threads/{id}/messages` | send, wait for the reply | `MessageOut` |
| `POST /v1/threads/{id}/messages/stream` | send, stream the reply | SSE: `token · progress · tool · citation · interrupt · done · error` |
| `GET /v1/approvals` | the manager's inbox | refunds waiting, across threads |
| `POST /v1/threads/{id}/resume` | approve · edit · reject | needs `Idempotency-Key`; 409 if nothing is paused |
| `GET /health` · `GET /ready` | liveness · readiness | unversioned, no model call |

`docs/api-reference.md` has every field and every error code.

### The approval cycle, and why "press approve twice" is safe

```
POST …/messages  "I want my money back"   → status: awaiting_approval, interrupt: {order, amount, why}
GET  /v1/approvals                        → the manager sees it
POST …/resume  Idempotency-Key: K1  {"type":"approve"}   → refund issued, reply returned
POST …/resume  Idempotency-Key: K1  {"type":"approve"}   → the SAME response, Idempotent-Replayed: true
                                                            (the graph is NOT resumed again)
```

The network can drop after the server has paid but before the app hears back. The app retries. Without
the key, that retry would resume the thread a second time. With it, the server recognises the decision
and replays its stored answer. The same key with a *different* body gets a 422, and a retry while the
first attempt is still running gets a 409. Session 11's idempotent `issue_refund` is the second line
of defence, so the money is protected even if this one fails.

### When a specialist breaks

`orders`, `knowledge` and `market` retry a failure twice (`RetryPolicy`). If they still fail, a
fallback (`llm/workflows/supervisor/nodes/fallback.py`) writes an honest "I couldn't check this right
now, a colleague will follow up", and the turn carries on. One dead carrier API no longer kills the
whole conversation.

## 7. What v10 still cannot do (session 14)

- **Anyone who finds the URL can read any thread and approve any refund.** There are no API keys yet.
- The knowledge base can only be changed by running a script on the server.
- One client can use up the whole model quota: there are no rate limits.
- Nothing tells a client which version of the API it is talking to, or what changed: no changelog,
  no releases.
- "Running" is tracked in memory, so it is correct for one server process only (session 16 runs
  several).
